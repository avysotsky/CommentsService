## Розгортання на власній інфраструктурі

Потрібні Docker Engine, Compose v2.24+, Git і Python 3. Docker збирає .NET/React;
SDK і Node на хості для розгортання не потрібні. Із кореня репозиторію:

```bash
python3 scripts/init-env.py
docker compose -p commentsservice --profile testing up -d --wait database test-database
python3 scripts/db-checkpoint.py
docker compose -p commentsservice build app
python3 scripts/db-command.py migrate
python3 scripts/db-command.py migrate --service test-database
docker compose -p commentsservice up -d --no-build --wait
curl --fail http://127.0.0.1:8080/health/database
```

Відкрийте http://localhost:8080 на Docker-хості. За потреби використовуйте sudo.
`commentsservice` — приклад назви проєкту; зберігайте її та файл оточення під час
оновлень, щоб використовувати попередні томи. Інший порт можна вибрати один раз:
`python3 scripts/init-env.py --port 8081`.

Тестова БД — окремий постійний сервіс профілю `testing`.
Перевірка контрольної копії охоплює обидві БД, тому спочатку запустіть обидві.
Міграції запускаються явно; застосунок не застосовує їх автоматично під час старту.
Перед оновленням схеми/даних зупиніть запис і перевірте контрольну копію.
Перехід 1.1.0.6 → 1.1.0.7 додав міграцію `20261030101720_CommentThreads`.
Зупиніть застосунок (`docker compose -p commentsservice stop app`), перевірте поточну
контрольну копію, зберіть випуск, явно застосуйте міграції обох БД та запустіть попередні томи.
Старі коментарі зберігають усі поля й стають коренями (`parentId=null`, `rootId=id`).
Зворотну міграцію заборонено за наявності відповідей; за потреби відновлюйте
перевірену копію до оновлення, враховуючи втрату змін після контрольної точки.

## Перевірка

```bash
python3 scripts/db-command.py check
python3 scripts/db-command.py check --service test-database
python3 scripts/test-backend.py
```

Для чотирьох наборів тестів потрібен SDK .NET 10 на хості. Тести читають створений файл
паролів і використовують `comments_test`. Тести БД відкочують транзакції; HTTP-тести видаляють
лише власні коментарі й записи авторів, що залишилися без посилань.
Для іншої машини/порту вкажіть `--host`/`--port` у команді тестів.
Скрипти команд БД і контрольних копій приймають `--env-file`, `--project` та повторюваний
`--compose-file`. Використовуйте однакові параметри в усіх командах розгортання.
Читання паролів розраховано на формат KEY=value, створюваний `init-env.py`.

`GET /api/status` повертає `{"application":"CommentsService","version":"1.1.0.10","stage":"ImageAttachments"}`.
`GET /health` перевіряє процес API; `/health/database` — підключення та незастосовані
міграції, повертаючи 503 за недоступності або застарілої схеми. Невідомі API-маршрути повертають 404; маршрути коментарів описані в docs/API.md.

## Паролі, зупинка та IDE

`init-env.py` створює приватний `.env` один раз і зберігає наявний файл.
Не публікуйте паролі та копії БД. Зміна .env не змінює пароль наявної ролі.
Застосунок слухає loopback; для зовнішнього доступу налаштуйте власний HTTPS reverse proxy.
Зупинка зі збереженням даних:

```bash
docker compose -p commentsservice --profile testing down
```

У Visual Studio 2026 відкрийте `CommentsService.slnx`; потрібні SDK .NET 10 і навантаження
ASP.NET/веб. Рішення збирає API й тести; Frontend містить редаговані файли React.
Docker збирає весь застосунок. Проміжні каталоги Windows і Linux розділено.
Без змінних БД API/сторінка статусу запускаються; перевірка БД повертає 503.
Для підключення з IDE задайте `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`
у приватному оточенні запуску. Не комітьте їхні значення.

## Архітектура Onion

Backend містить чотири проєкти: Domain, Application, Infrastructure та Api.

Infrastructure/Persistence містить Configurations, Repositories і Migrations.
HTTP endpoints використовують контракти застосунку/платформи; Infrastructure підключається в Program.cs.

першу міграцію й наявні дані; схема розширюється міграцією відповідей. Далі — 1.1.0.15 Acceptance.

## XHTML-редактор

Дозволено `a`, `i`, `strong`, `code`. Посилання потребує абсолютного HTTP(S) `href` без облікових даних; `title` необов’язковий. Решту атрибутів, простори імен, вкладені посилання, коментарі, DTD/CDATA, неправильну вкладеність і небезпечні адреси заборонено. XHTML потребує закритих тегів нижнього регістру та XML-сутностей (`&amp;`, `&lt;`, `&quot;`); звичайний текст `1 < 2 && 3 > 1` також дозволено. Обмеження: 65 536 одиниць UTF-16, глибина 32 та 4096 вузлів парсера.

Виділіть текст і натисніть «Жирний», «Курсив», «Код» або «Посилання». Посилання вставляє редагований HTTPS-шаблон. «Перегляд» надсилає `POST /api/comments/preview` з `{ "text": "<strong>Hello</strong>" }` та отримує `{ "html": "<strong>Hello</strong>" }` без звернення до БД чи запису. Збереження використовує той самий валідатор Application. Редагування приховує застарілий перегляд; помилка зберігає чернетку. Перегляд і таблиця створюють лише дозволені React-елементи, безпечні посилання та екранований текст у разі відмови. Наявні записи збережено; схема розширюється міграцією відповідей.

Підказка необов’язкового поля сайту вимагає повну адресу, наприклад `https://example.com`; `http://` також підтримується. Форма не обирає протокол і не перевіряє доступність сайту.

## Гілки коментарів

Відповісти можна на будь-який наявний коментар. Натисніть «Відповісти» під записом; форма покаже адресата. «Скасувати відповідь» повертає створення кореня й зберігає чернетку. Успішна відповідь з’являється під батьківським записом; відсутній адресат спричиняє помилку без створення автора чи коментаря.

Таблиця показує 25 коренів на сторінці у вибраному порядку. «Показати/Приховати відповіді» розгортає прямі відповіді; «Ще відповіді» завантажує наступні 25. Відповіді йдуть за часом UTC/UUID за спаданням, корені — у вибраному порядку. Глибина обговорення не обмежена застосунком: виведення ітеративне, візуальний відступ перестає зростати після шести рівнів, числовий рівень продовжує зростати. «Оновити» перечитує корені й відкриті гілки; помилка гілки пропонує «Повторити» та зберігає завантажений вміст. Повні сторінки/сортування коренів реалізовано в цій версії.

API: POST /api/comments приймає необов’язковий parentId (UUID/null); rootId визначає сервер, передавати його не можна. GET /api/comments/{id}/replies?limit=25&after={replyId} повертає {items,nextAfter}; для першої порції after не вказується. Limit — 1–100; after має бути прямою відповіддю цьому батьківському запису. Немає батьківського запису: 404 під час читання, помилка parentId (400) під час запису. Невідомий/чужий курсор — 400. Порції обмежують сусідні відповіді, а не глибину. API видалення/редагування не додано.

## Сортування та сторінки коренів

SPA завантажує `GET /api/comments/page?page=1&sort=createdAt&direction=desc`. Поля сортування: `userName`, `email`, `createdAt`; порядок: `asc` або `desc`. Типово дата спадає — LIFO. На сторінці **25 коренів**, без урахування відповідей. Відповідь API: `items`, `page`, `pageSize`, `totalCount` (лише корені), `totalPages`. Page — ціле 1–85 899 345; хибні поля/порядок дають 400. Після останньої сторінки API повертає порожній items із реальними підсумками; SPA виправляє застарілу адресу на останню сторінку або першу для порожнього списку. Для порожнього списку totalPages=0.

Доступні всі шість поєднань сортування; зміна повертає на першу сторінку. Перша/Попередня/Наступна/Остання та перехід за номером керують сторінками; адреса зберігає page/sort/direction під час перезавантаження. Чернетка не зникає. Новий корінь повертає на першу сторінку нових записів; відповідь зберігає поточну сторінку й не змінює кількість коренів. У відповідей попередні кнопки розгортання/приховування/дозавантаження. Помилка оновлення зберігає попередні результати; повтор — «Оновити».

Однакові значення впорядковано за UUID у тому самому напрямку. Ім’я/email використовують зіставлення БД, дата — UTC. Кількість і рядки читаються в одному repeatable-read знімку запиту. Різні запити сторінок відображають поточні дані: паралельне додавання може зміщувати offset-межі. Сумісний `GET /api/comments?limit=25` зберігає масив останніх коренів. Сортування не змінювало схему; у 1.1.0.10 додано міграцію зображень.

## CAPTCHA

Кожен коментар/відповідь потребує нової перевірки. `GET /api/captcha` повертає `{id,imageDataUrl,expiresAt}` із растровим PNG-зображенням та заголовками no-store; відповідь текстом чи метаданими не надається. Введіть шість латинських літер/цифр із зображення, регістр не важливий. Код діє **5 хвилин**. `GET /api/captcha?replace={oldId}` скасовує попередню перевірку та видає нову.

POST /api/comments додатково потребує `captchaId` (UUID) і `captchaCode`. Виклик перевірки витрачає ID, зокрема за хибної відповіді; відсутність, прострочення, заміна чи повтор дають 400 з `errors.captchaCode`, без підготовки автора/коментаря. Решту полів перевірено до CAPTCHA; після успішної перевірки помилка батьківського запису/сховища також витрачає код. Після невдалої чи невизначеної спроби оновіть зображення перед повтором. Перегляд і читання CAPTCHA не потребують.

Форма завантажує/оновлює зображення, блокує надсилання під час завантаження/прострочення/недоступності та зберігає чернетку за помилки. Після кожної спроби POST отримує нову перевірку. Підписи/помилки — EN/RU/UA. Сховище в пам’яті процесу обмежене 2 048 перевірками, звільняє прострочені записи та повертає 429 за заповнення. Перезапуск/перестворення застосунку скасовує решту кодів. Різні екземпляри мають окремі коди; для цієї версії використовуйте один екземпляр. PNG створюється переносимими засобами .NET без платформної графіки. У пам’яті лишаються лише хеш відповіді й термін; дані CAPTCHA та міграція в PostgreSQL не додаються.

## Зображення у вкладеннях

До кореня чи відповіді можна додати **одне необов’язкове JPG/JPEG, GIF або PNG**. Виберіть файл біля коментаря; «Прибрати зображення» очищає вибір. Межа джерела — 5 МіБ, 16 мільйонів декодованих пікселів та 10 000 пікселів на сторону. Великі зображення зменшуються пропорційно до 320×240 без обрізання; малі не збільшуються. Ураховано поворот JPEG за EXIF; GIF використовує перший кадр. Прийнятий файл заново кодується у статичний PNG, видаляючи початкові метадані та хвостові дані. Прозорість зберігається. Ці межі обрано застосунком; завдання потребує підтримувані формати й результат 320×240.

Сервер звіряє розширення з реальним кодеком, декодує зображення та відхиляє пошкоджені/обрізані дані до підготовки рядків БД. MIME браузера й accept не є доказом формату. Нормалізоване зображення зберігається з автором/коментарем одним unit of work у PostgreSQL; окремого файлу чи нового Docker-тому немає. Рядок містить байти (до 512 КіБ), безпечне відображуване ім’я, розміри й унікальний CommentId. У коментаря максимум одне зображення; видалення власника каскадно видаляє лише його. Видалення батьківського запису з відповідями лишається забороненим. Старим коментарям зображення не додаються.

JSON POST /api/comments зберігається для тексту без файлу. Із зображенням використовуйте multipart/form-data: ті самі текстові/CAPTCHA-поля й один файл `image`; boundary створює браузер/curl. Невідомі/повторні поля та кілька файлів відхиляються. JSON обмежено 1 МіБ; multipart — 6 МіБ на запит і 5 МіБ на файл. Хибне зображення дає 400 з errors.image; завеликий запит може дати 413. CAPTCHA витрачається до обробки зображення, тому повтор потребує нового коду. Помилка зберігає чернетку й файл; успіх очищає їх.

DTO коментаря містить nullable `image: {id,fileName,width,height}`; списки/сторінки/відповіді не містять бінарних даних. `GET /api/images/{id}` видає лише нормалізований PNG з image/png, inline-іменем на основі ID та X-Content-Type-Options: nosniff, або 404. Мініатюра відкриває вікно перегляду 1.1.0.12. TXT-вкладення реалізовано в 1.1.0.11. Обробка — [SkiaSharp 4.154.0](https://www.nuget.org/packages/SkiaSharp/4.154.0) і відповідні Linux native assets; повідомлення в [docs/third-party](docs/third-party/README.md) та образі застосунку.

Міграція `20261030122207_ImageAttachments` додає лише таблицю/індекс/перевірки/FK зображення; попередні поля/ID авторів/коментарів збережено. Down заборонено за наявності зображень.
