# Runtime limits / Рабочие ограничения / Робочі обмеження

## English

Version 1.1.1.17 RuntimeLimits moves operational limits into backend `config.json`, under `Runtime.Limits`, `Runtime.Captcha` and `Runtime.Requests`. The shipped values preserve Junior behavior: 25 roots/page, 100-character names, 254-character e-mail, 2048-character homepage, 65536-character comments, JPG/GIF/PNG uploads up to 5 MiB resized to 320×240, TXT up to 100 KiB, and a six-character, five-minute CAPTCHA. Required fields, mandatory single-use CAPTCHA, allowed formats/tags, safe URLs and SQL/XSS protections cannot be disabled through configuration.

`Limits` includes RootPageSize, DefaultListLimit, MaximumListLimit, UserNameMaxLength, EmailMaxLength, HomePageMaxLength, TextMaxLength, UserAgentMaxLength, MarkupMaxDepth, MarkupMaxNodes, ImageUploadMaxBytes, ImageMaxWidth, ImageMaxHeight, ImageDecodeMaxDimension, ImageDecodeMaxPixels, ImageProcessingConcurrency and TextFileMaxBytes. `Captcha` includes LifetimeSeconds, Capacity, CodeLength and Alphabet. `Requests` includes JsonMaxBytes, JsonMaxDepth, BodyMaxBytes, MultipartMaxBytes, FormValueMaxLength, FormValueCountLimit and HealthTimeoutSeconds. [Default configuration](../src/CommentsService.Api/config.json) lists every value.

Settings are validated before serving. RootPageSize accepts 1–100 (keep 25 for the assignment), MaximumListLimit 1–1000, DefaultListLimit 1–MaximumListLimit. Field and attachment limits may be reduced but cannot exceed the existing schema ceilings. Markup stays within depth32/nodes4096; image decoding within dimension10000/16million pixels; image concurrency1–8. CAPTCHA lifetime10–3600 seconds, capacity1–100000, length4–10, with at least eight distinct characters from the supported uppercase/digit glyph alphabet. JSON depth1–16; request ceilings cannot exceed shipped maxima, and JSON/multipart limits cannot exceed BodyMaxBytes. Form values require1–262144 characters and8–16 fields; health timeout1–60 seconds. Domain/schema constants remain fixed storage invariants, not mutable instance settings. Existing stored attachments remain readable when future-upload limits are reduced. No migration is required.

The SPA first requests `/api/config` with no cache. This explicit public allowlist contains field/upload/paging limits and CAPTCHA length/alphabet/lifetime, never database settings, passwords, paths, logging or proxy configuration. Validation, input lengths, queries, counters and EN/RU/UA hints use that response. A failed initial load shows Retry before the form is rendered. Restart the backend and reload the page after changes; there is no hot reload. Existing configuration priority and per-instance read-only mounts are unchanged; see [configuration](CONFIGURATION.md). Viewer and renderer safety guards retain fixed persisted/protocol ceilings so older data is not rejected by stricter future-input settings.

Verified: 305 backend tests (27/84/56/138), 28 frontend tests, frontend/Docker builds. A separate instance used page7, list3, name12, text120, TXT64bytes, image160×120 and CAPTCHA8characters/60seconds. Real Edge desktop/360px checks covered all three languages, oversized TXT rejection, actual CAPTCHA-backed image creation resized to160×80, and configuration failure/retry. All18 retained-million paging cases passed with three samples each, stable IDs and25 roots/page; no reseeding. Only owned test records/container were removed. Default public deployment reports1.1.1.17 and retains the original limits. Schema, databases, corpus, environment, volumes and checkpoints are preserved. Host reboot/autostart was verified on the preceding1.1.1.16; no additional reboot is claimed for this code update.

Защитные пределы просмотра/рендеринга остаются привязаны к хранилищу/протоколу, чтобы строгие настройки нового ввода не блокировали старые данные.
